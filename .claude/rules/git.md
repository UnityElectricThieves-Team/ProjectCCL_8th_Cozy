# Git 워크플로우

Project Cozy에서 우리가 git을 어떻게 쓰는지 정리한 문서예요. 합의의 결과물이니까, 바꾸고 싶은 부분 있으면 이 문서를 고쳐서 맞춰요.

## 브랜치 종류

- `main` — 마일스톤을 확인하는 브랜치. 평소에는 보지 않고, 한 단계가 끝났을 때 그 시점의 상태를 올려두는 용도로만 써요.
- `develop` — 작업이 합쳐지는 통합 브랜치. **모든 작업은 여기서 시작하고 여기로 모여요.**
- `feature/*`, `hotfix/*` — 한 가지 작업을 격리할 때 꺼내 쓰는 단기 브랜치. 끝나면 `develop`에 합쳐요. 워크트리(`git worktree`)로 꺼내 쓰면 여러 작업을 동시에 돌릴 수 있어요.

예전에 쓰던 `develop-<별명>` 상시 개인 브랜치는 더 만들지 않아요. 오래 갈라져 있으면 나중에 합칠 때 충돌이 커지는데, 특히 Unity 씬은 자동 머지가 안 돼서 손으로 풀어야 해요. 작업 단위로 짧게 꺼내 쓰고 바로 합치는 쪽이 안전해요. 남아 있는 `develop-<별명>` 브랜치는 예전 작업이에요.

## 변경사항 전파 방향

흐름은 하나예요. **아래에서 위로** — `feature/*` → `develop` → `main`.

| 변경 종류 | 시작점 | 흐름 |
|---|---|---|
| 코드 (기능/리팩터) | `develop`에서 직접, 또는 `feature/*`로 격리 | (`feature/*` →) `develop` → `main` |
| 개발 문서 (`Docs/Development/`, `CLAUDE.md`, `.claude/rules/`) | 코드와 같이 `develop` | `develop` → `main` |
| 급한 수정 | `hotfix/*` | 상황에 맞게 빠르게 |

**기획·디자인 문서는 저장소에서 다루지 않아요.** 기획은 Figma와 Notion에서 작업하고 그쪽이 정답이에요.
그래서 예전에 있던 "문서는 `main`에서 아래로 내려간다"는 흐름은 더 없어요. 저장소로 들어오는 변경은 전부 `develop`에서 시작해요.

`Docs/Planning/`에 남아 있는 문서들은 Figma·Notion 내용을 개발자가 1차로 해석해 옮겨둔 사본이에요.
원본과 어긋나면 Figma·Notion이 이기고, 이 사본을 고치는 것으로 기획을 바꿀 수는 없어요.

## `main`으로 올릴 때

`develop` → `main` 머지는 **마일스톤을 기록하는 일**이에요. 한 단계가 끝나서 "여기까지 됐다"를 남기고 싶을 때 올려요.
평소에 누가 보는 브랜치가 아니니까 급할 일은 없고, 올리기 전에 올릴 만한 상태인지 한 번 점검해주세요.

`develop`으로 합치는 건 절차 없이 바로 진행해요. 대신 아래 셀프 체크는 지켜주세요.

## 커밋 전 셀프 체크

커밋 올리기 전에 한 번씩만 봐주세요.

- Unity Console에 에러 없는지 확인.
- `git status`에서 의도치 않은 `.meta`나 `Project_Cozy/ProjectSettings/*` 변경이 묻어오지 않았는지 확인.
- 큰 바이너리(임시 빌드 산출물 등)가 섞이지 않았는지 확인.

## 커밋 메시지 컨벤션

prefix를 붙이면 나중에 히스토리 보기 편해요. 권장 사항이고 강제는 아니에요.

- `feat` — 새 기능
- `fix` — 버그 수정
- `refactor` — 동작 변화 없는 구조 개선
- `chore` — 설정 / 잡일
- `docs` — 문서
- `scene` — Unity 씬 변경
- `test` — 테스트

무리해서 지킬 필요는 없고, 어색하면 그냥 평문으로 적어도 돼요.

## 금지 사항

- `main`, `develop`에 force push 금지. 다른 사람 작업이 통째로 날아갈 수 있어요.
- 머지 충돌이 났을 때 `git checkout --ours` / `--theirs`로 한쪽을 통째로 버리는 것도 금지. 충돌 부분은 손으로 하나씩 풀어주세요.

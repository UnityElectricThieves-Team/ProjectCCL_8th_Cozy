# Git 워크플로우

Project Cozy에서 우리가 git을 어떻게 쓰는지 정리한 문서예요. 합의의 결과물이니까, 바꾸고 싶은 부분 있으면 디스코드에서 얘기하고 같이 고쳐요.

## 브랜치 종류

- `main` — 기획·디자인 문서랑 안정된 코드가 사는 브랜치. 기획자/디자이너가 평소에 보는 곳이라, 문서 변경은 여기에 바로 올려도 OK.
- `develop` — 개발자들의 작업이 합쳐지는 통합 브랜치.
- `develop-<별명>` — 개발자 각자 본인 브랜치. 별명이나 구분자(`-` / `_` 등)는 마음대로.
- `feature/*`, `hotfix/*` — 가끔 급한 일이 생기면 꺼내 쓰는 단기 브랜치.

## 변경사항 전파 방향

크게 두 흐름이 있어요.

- **문서는 위에서 아래로** — `main` → 각 개발자 브랜치.
- **코드는 아래에서 위로** — 각 개발자 브랜치 → `main`.

| 변경 종류 | 시작점 | 흐름 (합의 범위 포함) |
|---|---|---|
| 기획·디자인 문서 | `main`에 직접 커밋 (합의 불필요) | `main` → `develop` → 각 `develop-<별명>` (각자 pull) |
| 코드 (기능/리팩터) | `develop-<별명>`에서 작업 | `develop-<별명>` → *(개발자 3명 합의)* `develop` → *(전원 합의, 주요 버전)* `main` |
| 급한 수정 | `feature/*` 또는 `hotfix/*` | 상황에 맞게, 가능하면 빠르게 합의 |

문서 변경이 `main`에 올라오면, 기획자/디자이너가 따로 알려주지 않아도 각 개발자가 본인 브랜치로 알아서 pull 땡겨가요.

## 머지 합의 규칙

머지 방향에 따라 합의 범위가 달라요.

- **`develop-<별명>` → `develop`** — 개발자 3명이 OK 하면 머지.
- **`develop` → `main`** — 개발 인원 전원(4~5명)이 OK 해야 머지.

특히 `develop` → `main` 머지는 **주요 버전 업데이트**에 해당해요. 기획자/디자이너까지 포함해 모든 인원의 합의가 정말 중요하니까, 디스코드에서 충분히 얘기하고 진행해주세요.

"주요 버전"이 정확히 뭔지는 미리 정해두지 않고, 그때그때 다같이 합의해서 결정해요. 주요한 변화나 버전이 있을 때 정도로 생각해주시면 돼요.

## 커밋 전 셀프 체크

커밋 올리기 전에 한 번씩만 봐주세요.

- Unity Console에 에러 없는지 확인.
- `git status`에서 의도치 않은 `.meta`나 `Project_Cozy/ProjectSettings/*` 변경이 묻어오지 않았는지 확인.
- 큰 바이너리(임시 빌드 산출물 등)가 섞이지 않았는지 확인.

## 커밋 메시지 컨벤션

prefix를 붙이면 나중에 히스토리 보기 편해요. 권장 사항이고 강제는 아니에요.

- `feat` — 새 기능
- `fix` — 버그 수정
- `refactor` — 동작 변화 없는 구조 개선
- `chore` — 설정 / 잡일
- `docs` — 문서
- `scene` — Unity 씬 변경
- `test` — 테스트

무리해서 지킬 필요는 없고, 어색하면 그냥 평문으로 적어도 돼요.

## 금지 사항

- `main`, `develop`에 force push 금지. 다른 사람 작업이 통째로 날아갈 수 있어요.
- 머지 충돌이 났을 때 `git checkout --ours` / `--theirs`로 한쪽을 통째로 버리는 것도 금지. 헷갈리면 디스코드에 물어봐주세요.

# Git 워크플로우

Project Cozy에서 우리가 git을 어떻게 쓰는지 정리한 문서예요. 합의의 결과물이니까, 바꾸고 싶은 부분 있으면 디스코드에서 얘기하고 같이 고쳐요.

## 브랜치 종류

- `main` — 기획·디자인 문서랑 안정된 코드가 사는 브랜치. 기획자/디자이너가 평소에 보는 곳이라, 문서 변경은 여기에 바로 올려도 OK.
- `develop` — 작업이 합쳐지는 통합 브랜치. 평소 개발은 여기서 해요.
- `feature/*`, `hotfix/*` — 한 가지 작업을 격리할 때 꺼내 쓰는 단기 브랜치. 끝나면 `develop`에 합치고 지워요. 워크트리(`git worktree`)로 꺼내 쓰면 여러 작업을 동시에 돌릴 수 있어요.

예전에 쓰던 `develop-<별명>` 상시 개인 브랜치는 더 만들지 않아요. 오래 갈라져 있으면 나중에 합칠 때 충돌이 커지는데, 특히 Unity 씬은 자동 머지가 안 돼서 손으로 풀어야 해요. 작업 단위로 짧게 꺼내 쓰고 바로 합치는 쪽이 안전해요. 남아 있는 `develop-<별명>` 브랜치는 예전 작업이에요.

## 변경사항 전파 방향

크게 두 흐름이 있어요.

- **문서는 위에서 아래로** — `main` → `develop`.
- **코드는 아래에서 위로** — `develop` → `main`.

| 변경 종류 | 시작점 | 흐름 |
|---|---|---|
| 기획·디자인 문서 | `main`에 직접 커밋 | `main` → `develop` |
| 코드 (기능/리팩터) | `develop`에서 직접, 또는 `feature/*`로 격리 | (`feature/*` →) `develop` → `main` |
| 급한 수정 | `hotfix/*` | 상황에 맞게 빠르게 |

문서 변경이 `main`에 올라오면 `develop`으로 내려받아 쓰면 돼요.

## `main`으로 올릴 때

`develop` → `main` 머지는 **주요 버전 업데이트**에 해당해요. `main`은 기획자/디자이너가 평소에 보는 곳이라, 반쯤 만든 상태가 올라가면 혼란스러워요. 올리기 전에 디스코드에서 한 번 이야기해주세요.

"주요 버전"이 정확히 뭔지는 미리 정해두지 않고, 그때그때 합의해서 결정해요. 주요한 변화나 버전이 있을 때 정도로 생각해주시면 돼요.

`develop`으로 합치는 건 합의 절차 없이 진행해요. 대신 아래 셀프 체크는 지켜주세요.

## 커밋 전 셀프 체크

커밋 올리기 전에 한 번씩만 봐주세요.

- Unity Console에 에러 없는지 확인.
- `git status`에서 의도치 않은 `.meta`나 `Project_Cozy/ProjectSettings/*` 변경이 묻어오지 않았는지 확인.
- 큰 바이너리(임시 빌드 산출물 등)가 섞이지 않았는지 확인.

## 커밋 메시지 컨벤션

prefix를 붙이면 나중에 히스토리 보기 편해요. 권장 사항이고 강제는 아니에요.

- `feat` — 새 기능
- `fix` — 버그 수정
- `refactor` — 동작 변화 없는 구조 개선
- `chore` — 설정 / 잡일
- `docs` — 문서
- `scene` — Unity 씬 변경
- `test` — 테스트

무리해서 지킬 필요는 없고, 어색하면 그냥 평문으로 적어도 돼요.

## 금지 사항

- `main`, `develop`에 force push 금지. 다른 사람 작업이 통째로 날아갈 수 있어요.
- 머지 충돌이 났을 때 `git checkout --ours` / `--theirs`로 한쪽을 통째로 버리는 것도 금지. 헷갈리면 디스코드에 물어봐주세요.

# 다중 모니터 지원 — 구현 전에 챙길 것

이 문서는 "창을 어느 모니터에 띄울지 고르는 기능"을 구현하기 전에, 현재 창·뷰포트 스택이 어디서 걸리는지와
무엇을 미리 실측해야 하는지를 정리한 것입니다. 줄번호는 2026-11-01 시점 스냅샷입니다.

## 1. 요구사항과 확정한 결정

### 1.1 UX 요구사항

1. 인게임 뷰포트가 여러 모니터에 걸치지는 않는다.
2. 어떤 모니터에 띄울지 고를 수 있다. 선택지에는 번호와 해상도가 함께 보인다 (예: "1: 1920×1080").
3. UI·별·인게임 뷰포트가 선택에 따라 **다 같이** 옮겨간다.
4. Windows 배율(DPI) 설정 때문에 게임이 보이는 크기가 바뀌지 않는다 (§4.1).

기획 사본의 근거: `Docs/Planning/UserSettings.md:35`에 "주 디스플레이 설정 — 기본값 1, 다중 모니터 환경에서
캐릭터를 표시할 모니터 선택(오직 한 모니터에만 표시)"이 필수 항목으로 있습니다. 사본이므로 구현 전에
Notion 원본과 대조합니다.

## 2. 현재 구조에서 좋은 소식

**요구 3은 창을 옮기기만 하면 저절로 충족됩니다.** 게임 화면은 OS 창 하나(HWND 하나)에 전부 들어 있습니다.
UI 캔버스, 별, 달, 캐릭터, 장식, 배경이 모두 같은 창 안에서 그려지므로, 창을 다른 모니터의 작업 영역으로 옮기면
전부 함께 옮겨갑니다.

**"현재 모니터"를 기준으로 다시 계산하는 경로가 이미 있고, 버튼으로 실행할 수 있습니다.**
`WindowManager.TryGetMonitorInfo`(`WindowManager.cs:459`)는 `MonitorFromWindow(_hwnd, NEAREST)`로 *창이 지금 올라가 있는*
모니터를 찾습니다. 작업 영역 → 베이스 공간 → 카메라 프레이밍 → `ViewportConfirmed` 방송이 모두 이 한 점에서 시작합니다.
그리고 9월과 달리 지금은 설정 그래픽 탭의 "화면 다시 맞추기" 버튼이 `ViewportScreenSettings.ReadjustWindow()`
(`ViewportScreenSettings.cs:195`)를 부릅니다(`GraphicsTabController.cs:72`).

**월드의 가로 범위는 모니터가 바뀌어도 변하지 않습니다.** 베이스 공간의 폭은 항상 마스터 캔버스 폭(3840)이고
높이만 작업 영역의 종횡비를 따릅니다. 앵커는 마스터 캔버스 우하단에 고정입니다. 따라서 모니터를 바꿔도
**베이스 공간의 윗변만 오르내리고**, 바닥과 좌우는 월드에서 그대로입니다.

## 3. 모니터를 바꿀 때 일어나야 하는 일 (흐름 초안)

```
[설정에서 "2: 2560×1440" 선택]  또는  [선택한 모니터가 분리됨 → 주 모니터로]
  → SettingsManager에 선택 저장 (분리로 인한 폴백은 저장하지 않음)
  → 적용자(Gameplay)가 값 변화를 듣는다
  → 뷰포트 편집 중이면 미룬다 (§4.5)
  → Platform: 목표 모니터의 작업 영역(rcWork)을 구한다
  → Platform: 창을 그 작업 영역으로 옮긴다 (SetWindowPos)
  → (배율이 다른 모니터면) 창 크기가 다시 바뀌지 않았는지 확인하고, 필요하면 한 번 더 맞춘다 (§4.1)
  → ViewportScreenSettings: 베이스 공간 재계산 → 카메라 재프레이밍 → 뷰포트 클램프(저장 안 함) → ViewportConfirmed
  → 구독자들(배경 띠, 장식, 캐릭터 거주 영역)이 새 뷰포트를 받는다
  → 다음 프레임: Screen.width/height가 새 크기로 바뀌고 UI CanvasScaler가 다시 계산된다
```

부팅 때도 같은 흐름입니다. 다만 "현재 창이 있는 모니터"가 아니라 "저장된 선택 모니터"에서 시작해야 합니다.

`settings.md`의 규약대로 "OS와 맞닿는 설정은 Gameplay의 적용자가 Platform을 부른다"를 따릅니다. 항상 위·자동 실행을
거는 `DesktopIntegrationApplier`와 같은 자리입니다. `SettingsManager.Changed`는 어느 설정이 바뀌어도 울리므로,
적용자는 마지막으로 건 모니터와 다를 때만 창을 옮깁니다.

## 4. 챙겨야 할 것 — 영역별

위험도가 높은 순서입니다.

### 4.1 DPI 배율 — 가장 큰 미확인 항목

**배율이 무엇인가.** Windows 설정 › 디스플레이 › "배율"(100%, 125%, 150% …)입니다. 같은 4K 모니터라도 150%로 두면
Windows가 글자와 창을 1.5배 크게 그려서 작은 화면에서도 읽기 편하게 합니다. 모니터마다 따로 정할 수 있어서,
노트북 화면은 150%, 외장 모니터는 100%처럼 섞여 있는 경우가 흔합니다.

**D8 요구사항과 지금 설계.** 지금 게임은 UI와 월드 모두 **모니터의 실제 픽셀 폭**을 기준으로 크기를 정합니다
(CanvasScaler Match=Width, 베이스 공간 폭 기준 배율). 배율 설정은 계산에 들어가지 않으므로, 설계상으로는 배율을
바꿔도 게임이 차지하는 화면 비율이 그대로입니다 — D8이 원하는 동작입니다.

다만 이 설계가 실제로 성립하려면 **프로세스가 모니터별 DPI 인식(Per-Monitor v2)으로 돌아야 합니다.**
DPI 인식 모드는 OS가 좌표를 실제 픽셀로 줄지, 배율로 늘린 가상 좌표로 줄지를 정하는 프로세스 속성입니다.
- **모니터별 인식이면:** `GetCursorPos`, `GetWindowRect`, `GetMonitorInfo`, `SetWindowPos`가 모두 실제 픽셀을 주고받습니다.
  지금 코드가 그대로 맞고, 배율과 무관한 크기도 지켜집니다.
- **인식 안 함이나 시스템 인식이면:** Windows가 우리 창을 배율만큼 늘려 그립니다(흐릿해지고 커집니다 — D8 위반).
  좌표도 가상 단위로 나와서 클릭 통과 판정(`PollClickThrough`)과 커서 좌표(`TryGetCursorContext`)가 어긋납니다.
- **Unity 플레이어는 이미 모니터별 인식으로 돕니다 (2026-11-01 확인).** 우리 코드는 DPI 인식을 설정하지 않지만
  (`SetProcessDpiAwareness` 계열 0건), 빌드 실행 파일의 원본인 Unity 6000.3.10f1의
  `windowsstandalonesupport/Variations/win64_player_nondevelopment_mono/WindowsPlayer.exe`에 박힌 매니페스트가
  `<dpiAwareness>PerMonitorV2</dpiAwareness>`(구형 OS용 `<dpiAware>True/PM</dpiAware>`)를 선언합니다.
  이 프로젝트는 Mono 백엔드이고 설치된 플레이어도 Mono뿐이라 이 파일이 쓰입니다.
  인식 모드는 창이 만들어지기 전에 정해져야 하므로 스크립트에서 다시 설정할 필요도 없고, 설정하면 안 됩니다.
- 남은 확인은 빌드 실행 중 실제 모드를 한 줄 로그로 찍어 보는 것뿐입니다(E1). 매니페스트를 바꾸는 플레이어 설정은
  찾지 못했지만, 빌드 결과물로 한 번 닫아 둡니다.

**배율이 다른 모니터로 옮기면 창 크기가 다시 바뀌는가.** 모니터별 인식 창이 배율이 다른 모니터로 넘어가면 OS가
`WM_DPICHANGED`를 보내고 "권장 크기"를 제안합니다. Unity가 이 메시지를 받아 창 크기를 스스로 바꾸면, 우리가 맞춘
작업 영역 크기가 곧바로 덮입니다.
- **조사 결과 (2026-11-02) — 정황상 Unity가 창 크기를 다시 계산할 가능성이 높지만, 단정할 수는 없습니다.**
  - `UnityPlayer.dll`은 `GetDpiForWindow`, `GetDpiForMonitor`, `AdjustWindowRectExForDpi`, `GetSystemMetricsForDpi`,
    `SystemParametersInfoForDpi`, `EnableNonClientDpiScaling`을 씁니다. `AdjustWindowRectExForDpi`는 "이 DPI에서 이 크기의
    창 테두리를 포함한 rect"를 계산하는 함수라, DPI가 바뀔 때 창 크기를 다시 잡는 코드가 있다는 강한 정황입니다.
    다만 파일만으로는 그 결과로 크기를 실제로 바꾸는지 알 수 없습니다(`WM_DPICHANGED`는 숫자 상수라 문자열 검색에 안 걸림).
  - Unity 이슈 트래커에 같은 계열의 기록이 있습니다. "배율이 다른 모니터에서 시작하면 `Screen.width/height`가 틀린 해상도를
    보고"(2023.2.0b3에서 수정), "`.position`으로 배율이 다른 모니터로 옮기면 크기가 틀림, 위치를 두 번 넣어야 할 때가 있음"
    (2023.2.5f1에서 수정). 둘 다 우리 버전(6000.3) 이전에 고쳐졌지만, "두 번 넣기"라는 언급은 DPI 전환 때 크기가 한 번
    다시 잡힌다는 것을 시사합니다.
  - 공식 문서(`Screen.MoveMainWindowTo`)는 DPI·크기 변화에 대해 아무 말도 하지 않습니다.
- **그래서 확인을 기다리지 않고 방어적으로 만듭니다.** 창을 옮긴 뒤 몇 프레임 동안 창 rect를 다시 읽어 목표와 다르면
  한 번 더 `ApplyRegion`합니다. Unity가 크기를 바꾸든 안 바꾸든 결과가 같아지므로, 모니터 2대 없이도 안전합니다. 확인 비용은
  전환할 때 몇 프레임뿐이라 상주 비용이 없습니다.
- **모니터 1대로 같은 경로를 시험하는 방법:** 게임을 켠 채 Windows 설정에서 배율을 바꾸면(100% → 125%), 모니터를 옮길 때와
  같은 `WM_DPICHANGED`가 우리 창에 옵니다. Unity가 창 크기를 바꾼다면 작업 영역보다 커지거나 작아져서, 우하단에 붙은 UI와
  배경이 화면 밖으로 밀리거나 떠 보입니다. 로그 없이 눈으로 확인할 수 있습니다(E2').

**알아둘 성질 하나.** "배율과 무관"하다는 것은 *같은 모니터에서* 배율을 바꿔도 게임이 그대로라는 뜻입니다.
모니터끼리 비교하면 게임은 늘 모니터 폭에 비례하므로, 27인치 4K와 14인치 노트북에서 눈에 보이는 실제 크기(cm)는
다릅니다. 이것은 다중 모니터와 무관한 지금 설계의 성질입니다.

### 4.2 모니터 목록과 번호

모니터를 나열하는 코드가 지금은 하나도 없습니다. 방법은 둘입니다.

| 방법 | 장점 | 확인할 것 |
|---|---|---|
| Unity `Screen.GetDisplayLayout(List<DisplayInfo>)` | P/Invoke가 필요 없다. `DisplayInfo`에 이름·해상도·주사율·작업 영역(`workArea`)이 들어 있다 | `workArea`의 좌표계·단위가 Win32 `rcWork`와 같은지, 음수 좌표 모니터에서 어떻게 나오는지, 장치 이름이 없다는 점(D3) |
| Win32 `EnumDisplayMonitors` + `GetMonitorInfo`(MONITORINFOEX) | 지금 코드와 같은 값(`rcWork`)을 쓴다. 장치 이름(`\\.\DISPLAY2`)과 주 모니터 여부(`MONITORINFOF_PRIMARY`)를 얻는다 | 콜백 델리게이트를 static으로 보관(Platform 규칙), 에디터 가드 |

**D3(장치 이름 저장) 때문에 Win32 쪽이 필요합니다.** Unity `DisplayInfo`에는 장치 이름이 없습니다.

**번호(D1):** 주 모니터를 1번으로 두고, 나머지는 열거 순서대로 2, 3…을 붙입니다. 순서는 상관없다고 정했지만,
번호가 실행할 때마다 바뀌면 헷갈리므로 rect의 왼쪽 → 오른쪽 순서로 정렬해 고정합니다. 이 정렬은 순수 계산이라
`UnityEngine` 없이 써서 EditMode 테스트를 붙입니다(`HitTestCalculator`와 같은 방식).

Unity에는 `Screen.MoveMainWindowTo(DisplayInfo, Vector2Int)`라는 창 이동 API도 있습니다. 비동기이고 DPI 전환을
Unity가 처리해 줄 가능성이 있어 §4.1의 대안이 될 수 있습니다. 다만 위치만 옮기지 크기를 작업 영역에 맞추지는 않고,
우리가 입힌 borderless·레이어드 스타일과 충돌할 수 있습니다(실험 E3).

### 4.3 선택한 모니터를 어떻게 저장하나 (D2·D3)

- **필드:** `SettingsFileFormat`에 장치 이름(문자열)과 rect(정수 넷)를 둡니다. `ViewportFileFormat`처럼 `RectInt`를 그대로
  담지 않고 정수로 풉니다. 기본값은 "비어 있음 = 주 모니터"입니다. 이러면 옛 설정 파일이 저절로 주 모니터가 되고,
  `settings.md`의 "기본값을 바꿀 때는 키 이름도 바꾼다" 문제가 생기지 않습니다.
- **찾는 순서:** 장치 이름 일치 → rect 일치 → 주 모니터. 장치 이름은 드라이버 재설치·도킹 스테이션에서 바뀔 수 있고,
  rect는 배치를 바꾸면 바뀌어서, 둘을 함께 보면 한쪽이 바뀌어도 찾을 수 있습니다.
- **폴백은 저장하지 않습니다.** 모니터를 다시 꽂으면 원래 선택이 돌아와야 합니다. `ViewportScreenSettings`가
  "클램프로 줄어든 뷰포트는 저장하지 않는다"고 정한 것과 같은 원칙입니다.
- **저장 시점:** 설정 일반 탭 항목이면 바뀌는 즉시 저장합니다(`settings.md`). 그래픽 탭의 [저장] 흐름이 아닙니다.
- **부팅 순서는 이미 맞습니다.** `SettingsManager`는 `DefaultExecutionOrder(-100)`의 `Awake`에서 파일을 읽고,
  `ViewportScreenSettings.Start`는 10프레임 뒤에 창을 배치합니다. 이 실행 순서 숫자를 정리하자는 TODO가 따로 있으니,
  여기서 새 숫자를 더 박지 않습니다.

### 4.4 WindowManager(Platform)에 필요한 것

1. **모니터 목록 API** — 번호·장치 이름·주 모니터 여부·`rcMonitor`·`rcWork`.
2. **특정 모니터의 작업 영역을 돌려주는 API** — 지금의 `TryGetWorkAreaRect`(`:369`)는 `MonitorFromWindow` 기반이라
   "옮긴 뒤에" 불러야 맞습니다. 옮기기 전에 목표 모니터의 값을 알아야 하므로 모니터를 인자로 받는 버전이 필요합니다.
3. **옮긴 뒤 검증** — §4.1 때문에 창 rect가 목표와 같은지 다시 읽어 확인하는 경로.

이미 있는 것:
- `ApplyRegion(x, y, w, h)`(`:335`)는 가상 화면 좌표를 그대로 받으므로 다른 모니터로 옮기는 데 그대로 씁니다.
- `TryGetMonitorRect`(`:386`)는 호출자가 없지만 주석이 "다중 모니터 선택 등에 쓸 수 있어 남겨둔다"고 합니다.
- `ApplyMonitorFullscreen`(`:351`)은 작업표시줄을 덮으므로 쓰지 않습니다.

**새 코드의 위치.** `Platform/CLAUDE.md`의 "추후 후보"에 `Display/`(다중 모니터, DPI, 작업표시줄 회피 좌표 계산)가 적혀
있습니다. 모니터 열거는 HWND 소유자인 `WindowManager`와 책임이 달라 `Platform/Display/`로 분리합니다. 에디터에서는
가짜 모니터 1개만 돌려줍니다.

**옛 구현을 같이 켜지 않습니다.** `WindowAspectFitter`와 `BorderlessWindow`는 같은 HWND를 만집니다.

### 4.5 ViewportScreenSettings에 필요한 것

- **`RefreshBaseSpace`의 입력을 "선택한 모니터의 작업 영역"으로 바꿉니다.** 지금은 창이 있는 모니터를 읽습니다.
  부팅 때 창은 Unity가 처음 띄운 모니터에 있으므로(§4.9), 이대로면 선택과 무관한 모니터를 읽습니다.
  창을 먼저 옮기고 나서 지금처럼 `MonitorFromWindow`로 읽는 방법도 되지만, §4.1의 크기 재조정이 끼면 순서가 꼬이므로
  목표 rect를 직접 넘기는 쪽이 안전합니다.
- **"화면 다시 맞추기"와의 관계.** 버튼은 "지금 창이 있는 모니터"가 아니라 "선택한 모니터"에 다시 맞춰야 합니다.
  그렇지 않으면 사용자가 창을 다른 모니터로 끌고 가 버튼을 누를 때 선택과 실제가 갈라집니다. (지금은 창을 끄는
  경로가 없지만, 모니터 분리 때 Windows가 창을 옮기는 경우가 있습니다.)
- **편집 중에는 모니터를 바꾸지 않게 합니다.** 뷰포트 편집 중에는 클릭 통과가 정지되어 있고 프리뷰 뷰포트를 들고
  있습니다. 그 사이 베이스 공간이 바뀌면 프리뷰가 옛 기준으로 남습니다. 사용자가 고르는 경우는 편집 중에 설정
  패널이 숨어 있어 일어나지 않지만(UIManager가 편집 중 패널을 숨김), **모니터 분리는 편집 중에도 일어납니다.**
  편집이 끝날 때(`EditModeChanged(false)`)까지 미뤘다가 적용합니다. `IsReady` 전의 요청도 같은 방식으로 미룹니다.
- **그래픽 탭의 미저장 뷰포트.** `ReadjustWindow`는 이미 미저장 사각형(`_pendingViewport`)도 클램프합니다(`:208`).
  모니터 전환도 같은 함수를 지나면 따로 할 일이 없습니다.
- **`Screen` 크기는 한 프레임 늦게 바뀝니다.** 편집 핸들처럼 `Screen` 크기와 베이스 공간의 비율을 쓰는 쪽은 창 크기가
  실제로 바뀌는 다음 프레임까지 옛 값을 봅니다(`WindowServiceHandover.md` §6 "보류" 7번과 같은 현상).

### 4.6 뷰포트 저장값 (D4 — 공통)

뷰포트는 베이스 공간 px로 저장되고, 베이스 폭이 늘 같으므로 **가로 위치·폭은 어느 모니터에서나 같은 의미**입니다.
높이는 짧은 모니터로 가면 클램프로 줄어들고, 저장값은 그대로라 돌아오면 복원됩니다. 지금 구조 그대로이고
추가 작업이 없습니다.

### 4.7 월드 오브젝트

가로는 불변이고 **윗변만 움직이므로**, 걱정할 것은 높은 곳에 있는 것뿐입니다.

- **캐릭터:** `ViewportConfirmed` → `ViewportLivingAreaBinder` → `BaseCharacterController.SetLivingArea`로 거주 영역이 다시
  들어갑니다. 뷰포트 클램프는 높이와 y를 *줄이는* 방향뿐이라 지면이 올라가는 일은 없고, 지면이 내려가면 캐릭터는 떨어집니다.
- **장식:** 9월 이후 월드에 놓이게 됐습니다(`DecorationLayer`). 위치는 가로 하나를 베이스 공간 px로 저장하고 세로는 지면에
  맞추므로(`ShopInventoryFileFormat.cs:25-36`), 모니터 전환에 영향받지 않습니다. 기획의 "뷰포트를 저장할 때 걸친 장식은
  회수"는 사용자의 저장에 걸린 규칙이고, 모니터 전환의 클램프는 저장이 아니므로 회수를 일으키지 않습니다.
  가로가 불변이라 클램프로 장식이 뷰포트 밖에 놓이는 경우도 없습니다.
- **별·달:** 씬·프리팹에 고정된 월드 좌표이고 뷰포트 변경에 반응하지 않습니다. 월드 PPU가 100으로 바뀌어서(2026-10)
  9월에 계산한 값은 낡았습니다. 월드 y × 100 = 베이스 px이므로, 그 값을 가장 짧은 경우의 베이스 높이와 비교합니다.
  베이스 높이 = 작업 영역 높이 × 3840 / 작업 영역 폭입니다. 16:9(1080p, 작업표시줄 48px)는 약 2064, 21:9(3440×1440)는
  약 1554, 32:9(5120×1440)는 약 1044입니다. 세로 모니터는 오히려 6800 가까이 커집니다.
- **저장된 월드 좌표:** 없습니다. 좌표 변환 마이그레이션은 필요 없습니다.

### 4.8 UI

- **배율:** Match=Width라 모니터 폭을 따라 UI 크기가 바뀝니다. 4K에서 1080p 모니터로 가면 UI가 절반이 됩니다.
  월드도 같은 배율로 줄어 UI와 월드의 비율은 유지됩니다.
- **세로 모니터(D7):** 폭이 1080px이면 UI와 월드가 4K 대비 0.28배로 아주 작아지고, 베이스 공간은 위로 아주 길어집니다.
  지원하기로 했으니 빌드에서 읽을 수 있는 크기인지 봅니다. 그래픽 탭의 UI 크기 단계로 사용자가 키울 수 있는지도 같이 봅니다.
- **드래그된 패널:** `DraggablePanel`은 *드래그하는 순간에만* 캔버스 안으로 클램프합니다. 세로가 짧은 모니터로 옮기면
  위쪽에 옮겨둔 패널이 화면 밖에 걸친 채 남을 수 있습니다. 전환 뒤 열린 패널을 한 번 다시 클램프할지 E8에서 봅니다.

### 4.9 부팅 때 창이 처음 뜨는 모니터

Unity 플레이어는 시작할 때 자기가 정한 모니터에 창을 띄우고(기본 창 400×400), 우리는 10프레임 뒤에 창을 작업 영역으로
옮깁니다. 선택한 모니터가 다르면 **잠깐 다른 모니터에 떴다가 점프**하는 모습이 보일 수 있습니다.

- Unity는 마지막으로 쓴 모니터를 레지스트리에 기억하고 `-monitor N` 명령행 인자도 받는 것으로 알고 있습니다.
  **이 프로젝트 설정(Windowed)에서 실제로 어떻게 동작하는지 확인하지 않았습니다.**
- 창이 투명해서 점프가 거의 안 보일 수도 있습니다. 실측 후 신경 쓸지 정합니다(실험 E4).

### 4.10 모니터 분리 감지 (D5·D6·D9)

**지금 규약과 부딪힙니다.** `viewport-coordinates.md`는 "해상도를 바꾸거나 작업표시줄을 옮기거나 창이 다른 모니터로
넘어가도 저절로 다시 맞추지 않는다. 이런 변화는 드물어서 상주하며 계속 확인하는 비용을 들이지 않는다"고 정해 두었습니다.
D5(분리되면 자동으로 주 모니터)를 하려면 분리를 알아채야 하므로, 이 규약을 "모니터 구성 변화만 자동, 해상도·작업표시줄은
버튼"으로 고쳐야 합니다.

**감지 방법 (D9):**

| 방법 | 비용 | 걸리는 것 |
|---|---|---|
| WndProc에서 `WM_DISPLAYCHANGE` 받기 | 메시지가 올 때만 일한다. 상주 비용이 없어 위 규약의 취지와 맞는다 | GameScene의 `WindowManager`는 `_resizable: 0`이라 **WndProc 자체가 설치되지 않는다**(`WindowManager.cs:210-215`). 설치를 리사이즈와 떼어내야 하고, 그러면 `WM_GETMINMAXINFO`가 창 최대 크기를 `_maxSize`(1920×1080, `:54`)로 묶는 것도 같이 꺼야 한다 — 안 그러면 4K 모니터로 옮길 때 창이 1920×1080에 갇힌다. WndProc는 종료 시 크래시 이력이 있는 경로다(`UninstallWndProc` 주석) |
| 1초에 한 번 모니터 목록·선택 모니터 존재 여부 확인 | 할당 없이 짜면 무시할 만하다. 스레드 문제가 없다 | 규약이 피하려던 "상주 확인" 그 자체다. 분리 뒤 최대 1초 늦게 반응한다 |

**판정 규칙:** 감지했을 때 *선택한 모니터가 사라졌으면* 주 모니터로 다시 맞춥니다(저장값은 유지). 선택한 모니터가 다시
나타나면 그쪽으로 돌아갑니다 — D6의 "모니터 변경은 자동"에 해당합니다. 선택한 모니터가 그대로 있고 해상도만 바뀌었으면
아무것도 하지 않고 버튼에 맡깁니다(D6).

> D6의 "모니터 변경 시 자동"을 이 문서는 "설정에서 다른 모니터를 고를 때"와 "선택한 모니터가 분리·재연결될 때" 둘 다로
> 읽었습니다. 앞의 것만 뜻했다면, 재연결 때 원래 모니터로 돌아가는 동작은 빼도 됩니다.

### 4.11 음수 좌표

주 모니터의 왼쪽이나 위에 있는 모니터는 좌표가 음수입니다. `HandleNCHitTest`는 `lParam`을 signed short로 읽고,
`TryGetCursorContext`는 상대 계산이며, `RectInt`·`ApplyRegion`은 음수를 그대로 받습니다. 빌드에서 확인한 적은 없어서
테스트 항목으로만 둡니다(E7).

### 4.12 성능·그래픽 (위험 낮음, 측정만)

- **다른 GPU에 연결된 모니터:** 노트북 외장 모니터가 다른 GPU에 물려 있으면 GPU 간 복사 비용이 생길 수 있습니다.
- **주사율이 다른 모니터:** VSync를 끄고 `targetFrameRate`로 고정하므로 영향은 적습니다.
- **창 크기 변경:** 스왑 체인을 다시 만드는 일회성 비용이라 문제없습니다.
- **클릭 통과·항상 위:** 창 단위 스타일이라 모니터와 무관합니다. `ApplyRegion`은 `SWP_NOZORDER`라 Topmost가 유지되지만,
  이동 뒤 한 번 확인합니다.

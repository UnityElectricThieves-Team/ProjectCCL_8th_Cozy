크로마키에서
DWM 알파 창으로

과거 방식은 특정 색을 투명하게 지우는 ColorKey였다. 현재 방식은 Unity가 만든 알파 값을 DWM이 합성하고, 상호작용 가능 여부는 콜라이더와 UI를 기준으로 직접 판단한다.

현재 채택
DWM 알파 합성 + hover-aware 클릭 통과 + 창 크기=뷰포트
검정 콘텐츠와 반투명 UI를 보존하면서 합성 비용은 실제 창 면적으로 제어한다.

한눈에 보는 핵심 차이

이전 · ColorKey 크로마키

“검정이면 투명”처럼 특정 RGB 색을 제거한다. OS가 렌더 결과의 색을 보고 픽셀 단위로 클릭을 통과시킨다.

렌더 픽셀 색→ ColorKey 비교→ 픽셀별 통과

현재 · DWM 알파 합성

RGB와 알파를 함께 합성한다. 클릭은 매 프레임 콜라이더·UGUI·창 핫존을 검사해 창 전체 통과 비트를 토글한다.

OS 커서→ Unity Hit Test→ 창 통과 토글

기술 비교

항목이전 ColorKey현재 DWM 알파
투명 기준지정된 RGB 색과 같은가렌더 타깃의 알파 값이 얼마인가
검정 콘텐츠순검정 글자·그림에도 구멍이 생김검정 RGB라도 알파가 있으면 정상 표시
반투명 UI색 일치 여부만 보므로 자연스러운 반투명 표현이 어려움0~1 알파 농도를 그대로 합성 가능
클릭 표면실제 비키색 렌더 픽셀Physics2D 콜라이더 + UGUI 레이캐스트 + 창 핫존
클릭 통과 단위픽셀 단위WS_EX_TRANSPARENT 창 전체 단위
프레임 작업앱 측 폴링 없음커서 위치에서 점 질의 1회, 상태 변화 시에만 Win32 호출
아트 제약키 색을 콘텐츠에 사용할 수 없음색 제약 없음, 대신 콜라이더 관리 필요
창 면적주로 큰 투명 오버레이 유지평시 창 자체를 뷰포트 Rect로 축소
편집 모드불투명 EditRegion 모드로 전환모니터 전체 창 + 알파 0.45 딤 + 뷰포트 핸들
주요 클래스삭제된 OverlayWindow 계열WindowManager + ViewportScreenSettings

왜 OS 커서를 읽는가?
클릭 통과가 켜지면 Unity Input System의 포인터 위치가 멈출 수 있다. 그래서 통과 상태와 무관한 GetCursorPos를 사용해야 다시 캐릭터 위로 들어온 순간을 감지할 수 있다.

왜 창을 뷰포트만큼 줄이는가

평시

Windows 창 크기와 확정 뷰포트 크기가 같다. 창 밖은 렌더링도 DWM 합성도 하지 않는다.

편집 중

배치할 데스크톱 전체를 보도록 현재 모니터 전체로 잠시 확장한다.

저장·취소

확정 뷰포트로 다시 축소하고 카메라를 재프레이밍한 뒤 ViewportApplied를 발행한다. 뷰포트 밖에 남은 캐릭터를 어떻게 다룰지는 아직 정해지지 않았고, 이 이벤트를 받는 구현도 비어 있다.

실행 순서

WindowManager.AwakeHWND 획득 → borderless → DWM 알파 → topmost → WndProc 설치
ViewportScreenSettings.Start모니터 크기 확인 → 초기 뷰포트 적용 → 카메라 프레이밍
평시 Update커서 아래 Collider·UGUI·이동/리사이즈 핫존을 판정해 클릭 통과 상태 유지
편집 진입클릭 통과와 OS 리사이즈 정지 → 모니터 전체 확장 → 딤과 편집 핸들 표시
저장 또는 취소확정 뷰포트로 창 축소 → 카메라 재프레이밍 → ViewportApplied 발행 (밖의 캐릭터 처리는 미구현)

현재 남은 주의점

BitBlt 유지

useFlipModelSwapchain: 0이 현재 Unity 알파 창 경로의 전제다.

카메라 클리어

RGB는 검정, 알파는 0. HDR과 MSAA는 알파를 손상할 수 있어 꺼둔다.

빌드에서 검증

DWM 합성 결과는 Editor와 다르므로 시각·입력 튜닝은 Windows 빌드에서 확인한다.

남은 프로토타입

BorderlessWindow와 ClickThroughProbe는 별도 정리 대상으로 남아 있다.

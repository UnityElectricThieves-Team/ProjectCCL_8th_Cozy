# 정적 창 모델 이관 계획

> **범위**: [WindowViewportUIArchitecture.md](WindowViewportUIArchitecture.md)의 결정 — "창 = 작업 영역 고정(정적),
> 뷰포트 = 게임플레이 데이터" — 을 실제로 구현하는 절차.
> **작성**: 2026-07-27 · 기준 브랜치 `develop`
> **선행 조건**: `feature/viewport-stack` 머지 완료 (`ad7d3f9`) — **충족됨**
> **상태**: 적대적 검수 3종(버그·정합성 / 코드품질·설계 / 범위·단순성) 반영 완료. 고친 내용은 §9.
> ⚠️ **3단계(뷰포트 영속화)는 검수 이후에 추가되어 검수를 거치지 않았다.** 다른 단계와 독립적이고

## 2. 작업을 나누는 원칙

| | 누가 | 무엇을 |
|---|---|---|
| **코드 트랙** | Claude | `.cs`의 신규 작성·수정. 완료 기준은 **컴파일 통과 + 경고 없음 + 기존 참조 안 깨짐** |
| **씬·프리팹 트랙** | 국기님 | `.unity`·`.prefab` 편집, 인스펙터 값, 프리팹 배리언트, 빌드 실행과 눈으로 하는 검증 |

- `.unity`와 `.prefab`은 Claude가 직접 편집하지 않는다(`.claude/rules/unity/scenes.md`).
- **새 `.cs`를 만들어도 `.meta`는 손으로 쓰지 않는다.** 국기님이 Unity를 한 번 열면 생성되고,
  그것을 `.cs`와 **함께** 커밋한다. (이 계획에서 새 `.cs`는 3단계의 두 개뿐이다.)
- 창·투명·클릭 통과는 전부 `#if !UNITY_EDITOR` 안이라 **Editor에서 검증되지 않는다.**
  아래 verify는 명시가 없으면 전부 빌드 실행 기준이다.

## 3. 단계

**4단계다.** 검수에서 원래 6단계 중 둘(뷰포트 거주 강제, **창 rect** 영속화)이 이번 범위가 아니라는
판정을 받아 §7로 옮겼고, 원래 1·2단계는 중간 상태가 깨져서 합쳤다(§9). 그 뒤 **뷰포트** 영속화가
3단계로 새로 들어왔다 — 창 rect와 반대 방향의 결정이며, 이유는 §8의 2번에 적었다.

0·1·2단계는 순서대로 진행한다. 3단계는 나머지와 독립적이라 언제 해도 된다.

---

### 0단계 — 안전장치 먼저

**왜 먼저인가**: 1단계 이후 창이 작업 영역 전체를 덮는다. 클릭 통과가 고장 나면 그 영역의 모든 클릭을
흡수하므로 파급이 지금보다 훨씬 크다. 순서를 뒤집으면 안 된다.

#### 코드 (Claude)

**0-1. `ViewportScreenSettings.OnDestroy`에서 suspend 해제** — 한 줄짜리 진짜 수정.

지금 `OnDestroy`(`:95-99`)는 이벤트 구독만 풀고 `SetClickThroughSuspended(false)`를 부르지 않는다.
편집 중에 이 컴포넌트가 파괴되면 **창이 모든 클릭을 영구히 흡수한다.** `OnDisable`에도 같은 처리를 건다.

> 검수 결과 **매 프레임 재주장도 만료 감시(watchdog)도 넣지 않는다.** 수명주기 실패는 이 한 줄이
> 결정론적으로 덮고, 로직 실패(예: `SaveEdit` 도중 예외로 `ExitEdit`에 도달 못 함)는 §7.6의 핫키가
> 들어와야 덮인다.
> 폴링을 넣으면 지금 `Update()`가 없는 클래스에 매 프레임 진입점이 생기고(이 프로젝트의 최우선 가치와
> 충돌), 만료를 넣으면 `Platform/`이 상위 레이어의 프레임 주기를 전제하게 된다.

**0-2. 비상 탈출 핫키 — 보류 (2026-07-27, 국기님 판단).** 어떤 키를 쓸지 정하지 않았다. §7.6으로 옮겼다.

#### 씬 (국기님)

없다. 이 단계는 코드 한 곳만 고친다.

#### verify (빌드)

1. 편집 진입 → 저장 → 클릭 통과가 돌아오는가.
2. 편집 진입 → 취소 → 클릭 통과가 돌아오는가.
3. 평상시 클릭 통과가 이전과 같은가 (회귀 없음).

> 원래 여기 있던 "편집 컴포넌트를 강제로 파괴" 항목은 **삭제했다.** 빌드된 실행 파일에 컴포넌트를
> 파괴할 수단이 없어 판정이 불가능했다. 0-1이 고치는 경로는 **코드 리뷰로만 확인한다.**

#### 핫키를 미루는 동안 남는 위험

0-1은 **수명주기 실패**(컴포넌트가 파괴·비활성화됨)를 덮는다. 덮지 못하는 것은 **로직 실패** —
예를 들어 `SaveEdit` 도중 예외가 나서 `ExitEdit`에 도달하지 못하면 컴포넌트는 멀쩡히 살아 있고
suspend만 켜진 채 남는다. 그러면 창이 작업 영역 전체의 클릭을 흡수하고, **앱 안에서 빠져나올
수단이 없다.**

다만 작업표시줄은 덮이지 않으므로(결정 문서 §3.2) 거기서 앱을 닫을 수 있다. 즉 복구가 불가능하지는
않고, "강제 종료가 유일한 수단"인 상태다. 핫키가 들어오기 전까지 이 상태로 간다.

### 1단계 — 작업 영역 기준 + 창 정적화 (핵심, 한 커밋)

**원래 두 단계였는데 합쳤다.** 좌표 기준만 작업 영역으로 옮기고 창 정적화를 미루면, 중간 상태에서
편집 모드가 깨진다 — `EnterEdit`의 `ApplyMonitorFullscreen()`은 `rcMonitor`(1920×1080)로 창을 잡는데
베이스 공간은 작업 영역(1920×1032)이 되어, 창 크기 ≠ 프레이밍 rect 크기가 된다. 그러면 화면이 4.65%
확대되고 가로 약 85px이 잘리며, `ViewportEditHandles`가 축마다 다른 배율(`sx=1.0`, `sy=1.0465`)로
핸들을 그려 "보이는 곳 ≠ 잡히는 곳"이 된다.

#### 코드 (Claude)

**1-1. `WindowManager.cs`**
- 작업 영역 rect를 돌려주는 API 추가. `MONITORINFO.rcWork`는 `TryGetMonitorInfo`가 이미 읽고 있다.
- `TryGetMonitorRect`(`:312-321`)는 **남기되 호출자가 0이 되는 이유를 주석에 적는다.** 안 적으면
  다음 사람이 "쓰는 곳이 없는데 왜 있지"를 다시 판다.
- `ApplyMonitorFullscreen`(`:300-308`)에 deprecated 주석. **`[Obsolete]` 특성은 붙이지 않는다** —
  경고가 나면 "경고 없음" 완료 기준과 충돌한다.
- `_maximizeToWorkArea` 토글(`:36`)과 `ApplyMaximizeAfterReady`(`:263-267`)에 **주석 + 인스펙터
  `Tooltip`**: "창 배치의 주인은 정책 레이어다. 이 토글은 `ViewportScreenSettings`가 없는 씬 전용."
  이걸 안 하면 창을 놓는 기계장치가 둘이 되고, 체크박스 하나가 코드의 불변식을 지키는 구조가 된다.

**1-2. `ViewportScreenSettings.cs`**
- `RefreshBaseSpace()`가 작업 영역 API를 쓰게 변경. 필드 `_monitorRect`를 **`_baseSpaceScreenRect`** 로
  개명한다(출처가 아니라 이 코드 안에서의 역할을 이름으로 삼는다). Editor 폴백은 그대로.
- **`ApplyNormal()`을 둘로 가른다.**
  - `ApplyScreenLayout()` (신규) — 작업 영역을 읽어 창을 그 rect에 놓고, 카메라를 베이스 공간 전체로
    프레이밍한다. `Start()`와 2단계의 재조정이 부른다.
  - `PublishViewportApplied()` — `ViewportApplied` 이벤트 발행만 한다. `ApplyNormal`이라는 이름은
    지운다. 창을 건드리지 않게 된 함수에 그 이름을 남기면 거짓말이 된다.
- `EnterEdit()`에서 `ApplyMonitorFullscreen()` 호출과 카메라 재프레이밍을 **제거**한다. 창은 이미
  작업 영역 전체이고 카메라도 이미 베이스 공간 전체를 비추고 있다.
  `SetClickThroughSuspended(true)`는 **남긴다**(편집 중 빈 공간에서 핸들을 끌어야 한다).
- `EnterEdit()`의 `RefreshBaseSpace()` 단독 호출을 없앤다. 베이스 공간 갱신은 **창·카메라 재적용과
  한 묶음으로만** 일어나야 한다. 지금처럼 베이스 공간만 갱신하면 창·카메라는 옛 값이라
  `ViewportEditHandles`의 `Screen.width ÷ BaseSpaceSize` 비율이 어긋난다.
- `WindowRectChangedByUser` 구독 제거.

**1-3. `WindowMoveResizeGuide.cs`** — 안내를 끈다. **5단계로 미루면 안 된다.**

이 컴포넌트는 테스트 패널이 런타임에 장착하므로 GameScene 빌드에서 **항상 그려진다**. `_resizable`을
끄면 조작은 죽는데 안내는 남아, 작업 영역 상단 중앙에 "≡ 창 이동" 그립이, 4변에 리사이즈 라인이
계속 표시된다. IMGUI라 UGUI 레이캐스트에 안 잡혀 클릭은 바탕화면으로 통과한다 — 이 저장소가 지키는
"보이는 곳 = 잡히는 곳" 원칙의 정면 위반이다.

**1-4. 코드 주석 정리** (같은 커밋에)

이번 변경으로 **거짓이 되는 주석들**이다. 문서만 고치고 주석을 놔두면 코드가 문서보다 오래 거짓말한다.

#### 이 단계가 만드는 변화 — 정확히 무엇인가

**뷰포트 설정이 화면에 아무 영향도 주지 않게 된다.** 지금은 뷰포트를 줄이면 창이 줄어 그 밖이
잘려 보이지 않는데("잘라내기에 의한 가둠"), 창이 정적이 되면 잘라낼 것이 없어진다.

**이것은 이번 이관에서 메우지 않는다.** 이유는 §7.1에 적었다 — 요약하면, 플레이어가 그 상태에
도달할 경로가 아직 없다.

함께 알아둘 부수 변화 둘.

- **스폰 위치**가 `Camera.main.transform.position` 기준인데(`WindowFeatureTestPanel.cs:97-99`),

## 7. 이번에 하지 않는 것

### 7.1 뷰포트 거주 강제 — **일부 구현됨 (2026-07-27)**

원래 이 계획의 3단계였다가 검수에서 "플레이어가 뷰포트를 줄일 경로가 아직 없다"는 이유로 빠졌는데,
국기님이 테스트 패널로 실제로 줄여 쓰시면서 **캐릭터가 뷰포트 밖으로 나가는 것이 바로 문제가 되어**
예정보다 앞당겨 구현했다. 검수의 판정이 틀렸다기보다, 전제("아무도 뷰포트를 줄일 수 없다")가
개발 중에는 성립하지 않았다.

**구현한 것 — 나가지 못하게 막는 쪽(예방)**

| 무엇 | 어디 |
|---|---|
| 살아있는 캐릭터 순회 API | `CharacterManager.Alive`(`IReadOnlyList`, 할당 없음) + `Registered` 이벤트 |
| 씬 배치 캐릭터도 추적 | `CharacterManager.Start()`가 씬을 한 번 훑어 `Register`한다. 이게 없어서 `FirstCharacter`만 규칙이 안 걸리는 버그가 실제로 났다 |
| 최초 캐릭터 보장 | `CharacterManager`가 시작 시 캐릭터가 0마리면 한 마리 스폰. 씬에 직접 놓는 방식을 대체한다 |
| 뷰포트 → 월드 영역 환산·배포 | 신규 `Gameplay/Viewport/ViewportLivingAreaBinder.cs` |
| 거주 영역 수용 | `BaseCharacterController.SetLivingArea(Rect)` |
| 걷기 클램프 | `MoveHorizontal`이 `bool`을 반환하고, 막히면 `WalkState`가 돌아선다 |
| 드래그 클램프 | `SetWorldPosition` |
| 지면이 뷰포트를 따라 움직임 | `FloorY = 거주영역 아래 변`. 서 있던 캐릭터는 새 바닥으로 옮겨 붙인다 — Idle/Walk는 접지를 다시 보지 않아서 값만 바꾸면 공중에 뜬 채 남는다 |

**`_floorY`의 의미를 바꾸지 않았다.** 검수가 경고한 "필드 하나가 두 뜻을 갖는 문제"를 피하려고,
절대 월드 y라는 뜻을 그대로 두고 **거주 영역이 있으면 그쪽이 이긴다**는 형태로 만들었다.
덕분에 이름을 바꿀 필요도, 여섯 군데 read site를 손볼 필요도 없었다. 직렬화된 `_floorY`는
이제 거주 영역이 없는 씬(TestHyeonScene 등)에서 쓰는 대체값이다.

> 처음에는 `max(_floorY, 아래 변)`으로 두어 기존 화면 높이를 보존했는데, **뷰포트 아래 변이
> 월드 y=7보다 낮을 때 지면이 따라가지 않아** 빌드에서 문제가 됐다(2026-07-30). 기획서 §2.1.1대로
> 뷰포트 아래 변 그 자체로 바꿨다.

### 함께 드러난 프리팹 오설정 — `_footOffset`

`Character.prefab`의 `_footOffset`이 `(0, 0)`인데 스프라이트는 **중앙 피벗**이다
(`pivot: 0.5, 0.5`, 프레임 256px ÷ PPU 14 = 18.29 유닛, 맞춰둔 BoxCollider2D는 원점 중심 16×16).
즉 코드가 "발"로 아는 지점이 실제로는 캐릭터의 한가운데라, 지면에 발을 맞추면 몸의 아래 절반
(약 8 유닛 ≈ 86px)이 지면 아래로 내려간다.

이건 이번 작업이 만든 것이 아니라 **원래 있던 오설정**이다 — `_footOffset`의 툴팁부터
"센터 피벗 스프라이트는 보통 y를 음수(발이 원점 아래)로 둔다"고 적고 있다. 지면이 고정된 월드
직선이던 동안에는 아트가 그 선에 맞춰 보이기만 하면 됐기 때문에 드러나지 않았다.

→ **`_footOffset.y`를 약 `-8`로.** 정확한 값은 아트의 발 위치라 눈으로 맞춰야 한다.
씬 뷰에서 캐릭터를 선택하면 기즈모가 발 지점을 **노란 구**로, 지면을 **초록 선**으로 그린다.

> **[2026-08-02 이후 무효]** 이 처방은 채택되지 않았다. `_footOffset` 필드 자체를 없애고
> **루트가 곧 발**이 되도록 프리팹에서 Visual 자식을 올리는 쪽으로 갔다. 오프셋을 필드로 들면
> 그 필드를 부르는 코드만 옳아지고 `transform.position`을 읽는 코드는 계속 틀리기 때문이다.
> 현행 규약은 [character-ground.md](../../.claude/rules/unity/character-ground.md).
> 아래 §의 `_floorY`·`_groundContactThreshold` 관련 서술도 같은 변경으로 낡았다 —
> 이 문서는 그 시점의 기록으로 남긴다.

**아직 안 한 것 — 이미 나간 것을 되돌리는 쪽(회수 연출)**

기획서 §2.1.1은 "캐릭터는 조금이라도 이탈하면 **'펑' 연출과 함께 뷰포트 내 랜덤 위치로 재스폰**"이라고
정한다. 지금은 그 대신 `SetLivingArea`가 **조용히 경계 안으로 끌어당긴다.** 연출도 랜덤 위치도 없다.
`ViewportResidencyEnforcer`는 여전히 본문이 주석 처리된 채로 남아 있고, 그 안의
"강제로 위치를 옮기는 것이 게임 디자인상 적절한가"라는 국기님 TODO도 그대로다.

또 **편집 중 프리뷰에는 반응하지 않는다.** 저장·취소로 확정된 순간에만 적용된다 — 기획서가
"조정 중에는 뷰포트 밖으로 나간 대상도 사라지지 않는다"고 정하고 있고, 핸들을 끄는 동안 캐릭터가
따라 끌려다니면 조작이 어렵기 때문이다.

**회수 연출을 할 때 볼 것** (검수에서 나온 함정들. 예방 쪽은 이미 처리했으므로 남은 것만 적는다):

- **지면 값만 바꾸면 서 있는 캐릭터는 안 움직인다.** `IsFootOnGround`/`IsFootBelowGround`는
  Fall Tick·Grabbed 릴리즈·StartUp에서만 불린다(`FallState.cs:21`, `GrabbedState.cs:28`,
  `StateModule.cs:98`). Idle/Walk 중에는 아무도 지면을 다시 안 본다.
  지금 구현은 `SetLivingArea`가 위치를 **직접** 옮겨서 이 문제를 피했다. 재스폰으로 바꿀 때
  "값만 바꾸고 상태 전이는 안 거는" 방식으로 되돌아가지 말 것.
- **가로 클램프와 재스폰은 같은 요구의 두 구현이다.** 지금은 클램프를 골랐으므로 걸어서 나가는
  경우가 아예 없고, 재스폰이 발화할 여지는 "뷰포트를 캐릭터 밑에서 줄였을 때" 하나뿐이다.
  기획서대로 '펑' 연출을 넣는다면 그 한 경우를 대상으로 하고, 클램프와 **겹쳐 넣지 말 것**.
- **경계는 발 기준이다.** 스프라이트 bounds로 잡으면 프레임마다 크기가 달라 경계가 떨린다
  (`_footOffset`이 존재하는 이유와 같다). 그래서 스프라이트 일부가 경계 밖으로 걸쳐 보일 수 있다.
  이걸 없애려면 프레임 크기 정규화가 선행되어야 한다.

`WindowGuideUGUIMigrationPlan.md`의 이관을 뷰포트 rect 기준으로 진행하는 작업(결정 문서 §5.3).

### 7.4 `ViewportScreenSettings` 분리

## 8. 남은 결정

1. ~~비상 탈출 핫키를 어떤 키로 할지~~ — **보류 확정 (2026-07-27).** §7.6으로 옮기고 TODO에 등록했다.
   기획 §2.4의 Boss Key(F2)는 "캐릭터 숨김"이라 다른 기능이니 겸용하지 않는다.
2. **재조정 버튼에 창 크기를 파일로 저장하지 않는 것에 동의하시는지.**

   창이 "항상 작업 영역"이면 켤 때마다 다시 계산하면 되므로 저장할 상태가 없다. 저장하면 오히려
   저장했기 때문에 생기는 문제(저장된 창이 지금 모니터보다 커서 조작 불가)를 처리할 규칙이 따로 필요해진다.

   **세션 중 동작은 두 안이 완전히 같다.** 작업표시줄을 옮겨도 창은 그대로고, 버튼을 눌러야 맞는다.
   갈리는 것은 재실행할 때뿐이다 — 저장하면 옛 자리를 유지하고, 저장 안 하면 새 작업 영역에 맞는다.

   저장하는 쪽에 문제가 하나 있다. 작업표시줄을 아래에서 위로 옮기면 옛 자리의 창이 **새 작업표시줄을
   덮는다.** 이 구조를 고른 두 번째 이유가 "버그가 나도 작업표시줄은 살려둔다"였는데, 저장하면 버튼을
   누르기 전까지 그 안전장치가 깨진 채로 남는다. 세션 중에는 어차피 그렇게 되지만(요구 ③이 받아들인
   대가다), 재실행은 다시 맞출 자연스러운 기회이고 저장하지 않으면 그때 안전장치가 공짜로 복구된다.

    → **확정 (2026-07-27, 국기님): 창 rect는 저장하지 않는다.** 요구를 문자 그대로 읽으면 어긋나는
   지점이 맞지만, 어긋나는 방향이 "안전한 상태로 스스로 돌아온다"이다.

3. **뷰포트는 저장한다** — 확정 (2026-07-27, 국기님). 창 rect와 반대 방향이고, 그게 맞다.

   두 값의 성격이 다르다. **창 rect는 작업 영역에서 언제든 다시 유도할 수 있는 파생값**이라
   저장하면 원본과 어긋날 위험만 생긴다. **뷰포트는 사용자가 직접 정한 원본**이라 어디서도 유도할 수
   없고, 저장하지 않으면 재실행 때마다 사라진다.

   원래 계획은 이걸 정확히 거꾸로 하고 있었다 — 파생값은 저장하고 원본은 안 하는 상태였다.
   구현은 §3의 3단계.

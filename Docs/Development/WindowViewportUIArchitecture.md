# 창·뷰포트·UI 구조 결정

> **목적**: 데스크톱 펫의 OS 창과 인게임 뷰포트를 어떤 관계로 둘지 결정한다. 구현 문서가 아니라 결정 문서다.
> **최종 결정일**: 2026-07-27 (2026-07-26 결정을 뒤집음 — §2에 이력)
> **배경 문서**: [WindowServiceHandover.md](WindowServiceHandover.md) §2·§6, [ViewportStackMigration.md](ViewportStackMigration.md) §3·§4·§8,
> [UIMenuBarDesign.md](UIMenuBarDesign.md) §3·§7, [Docs/Planning/UserSettings.md](../Planning/UserSettings.md) §2.1.1

## 1. 결정

**창은 작업 영역(모니터에서 작업표시줄을 뺀 영역)에 고정한다. 뷰포트는 OS 창과 분리되어
순수한 게임플레이 데이터가 된다.**

| 개념 | 새 정의 |
|---|---|
| **OS 창** | 항상 현재 모니터의 **작업 영역** 전체. **정적** — 사용자가 "윈도우 크기 재조정"을 누를 때만 다시 잡는다. 평상시에는 크기도 위치도 변하지 않는다 |
| **베이스 공간** | = 작업 영역 = 창. 마스터 캔버스(3840×2160)의 우하단을 작업 영역 크기만큼 잘라낸 영역 |
| **뷰포트** | 베이스 공간 안의 논리적 사각형. **렌더링 파라미터가 아니다.** 캐릭터 이동 제한, 지면 위치, 시설물 배치·회수 판정, 편집 핸들의 대상 |
| **카메라** | 베이스 공간 전체를 1:1 절대 픽셀로 프레이밍. 재조정 때 말고는 **다시 건드리지 않는다** |

이것은 이 세션이 검토한 세 안 중 **1번(창을 항상 모니터 전체로)의 변형**이다. 원안과 두 가지가 다르다.

- 모니터 전체가 아니라 **작업 영역**이다 — 작업표시줄을 절대 덮지 않는다 (§3.2).
- **`camera.rect`를 쓰지 않는다.** 원안은 "뷰포트만 그리려면 `camera.rect`가 필요하다"고 전제했는데,
  그럴 필요가 없다 (§3.3).

### 함께 확정한 것

| 항목 | 결정 |
|---|---|
| 베이스 공간의 정의 | 모니터 해상도 → **작업 영역**으로 변경. 기획 원본 반영 필요 (§7.1) |
| 창 이동·리사이즈 기계장치 | **deprecated로 살려둔다.** 상당수가 뷰포트 리사이즈에 재사용된다 (§5.2) |
| `WindowGuideUGUIMigrationPlan.md` | **예정대로 진행.** 대상이 창 안내에서 뷰포트 안내로 바뀐다 (§5.3) |

## 2. 이력 — 이 문서는 하루 만에 뒤집혔다

2026-07-26에 이 문서는 **2번(하이브리드 — 평시 창=뷰포트, UI 패널이 열린 동안만 모니터 전체로 확장)**
을 채택했다. `ViewportStackMigration.md` §8이 기록한 것과 같은 결론이었다.

2026-07-27에 뒤집었다. 이유는 셋이고, 첫째가 결정적이다.

### 2.1 메뉴 바가 화면 우하단 고정이라 "창=뷰포트"가 성립하지 않는다

`UIMenuBarDesign.md` §3의 `MenuButtonBar`는 RectTransform 앵커·피벗이 우하단 `(1, 0)`이고
`ScreenSpaceOverlay` 캔버스에 붙는다. 즉 **창의 우하단**에 붙는다.

창=뷰포트에서는 창의 우하단이 곧 뷰포트의 우하단이므로, 사용자가 뷰포트를 좌상단으로 옮기면
메뉴 바도 화면 좌상단으로 따라간다. 메뉴 바를 화면 우하단에 두려면 **창이 항상 화면 우하단
모서리를 포함해야 한다.**

하이브리드로도 메꿀 수 없다. 확장은 패널이 열린 동안만인데 메뉴 바는 상시 보여야 한다.
그리고 뷰포트가 좌상단, 메뉴 바가 우하단이면 둘을 감싸는 사각형은 이미 거의 모니터 전체다.

### 2.2 전체 화면 점유 상태에서 입력이 막히면 복구 수단이 없다

클릭 통과는 창 단위 `WS_EX_TRANSPARENT` 토글이다. 폴링이 멈추거나 `_clickThroughSuspended`가
켜진 채 남으면 **창이 덮은 영역의 모든 클릭을 흡수한다.** topmost + 전체 화면이면 사용자 입장에서는
바탕화면이 잠긴 것과 같고, 복구 수단은 강제 종료뿐이다.
(`WindowGuideUGUIMigrationPlan.md` §4.2가 같은 위험을 이미 지적하고 있다.)

이건 하이브리드에도 있던 위험이다 — `ApplyMonitorFullscreen()`이 `rcMonitor`를 쓰므로
확장 중에는 작업표시줄까지 덮는다. **어느 모델을 고르든 고쳐야 할 문제였다.**

### 2.3 1번을 기각할 때 쓴 근거 하나가 틀렸다

7-26 판에서 1번을 기각하며 이렇게 적었다.

> **검증되지 않은 위험을 새로 들인다.** `camera.rect`를 설정했을 때 `Camera.ScreenToWorldPoint`가
> 어떻게 동작하는지 … `WindowManager.PollClickThrough`가 이 API로 클릭 통과를 판정하므로 …

**`camera.rect`가 애초에 필요 없다.** 자세한 것은 §3.3. 이 오류 때문에 1번의 비용을 실제보다
비싸게 평가했다.

### 2.4 살아남은 것 — 좌표계 유도는 여전히 유효하다

7-26 판 §4의 유도(창 크기가 달라져도 화면상 위치·크기가 픽셀 단위로 같다)는 **그대로 맞고,
새 모델에서 더 중요해진다.** §4에 옮겨 두었다. 이것이 "윈도우 크기 재조정"이 캐릭터를
움직이지 않는다는 보증이다.

반대로 7-26 판 §5(확장 요청 중재, `UIManager` 훅)는 **전부 불필요해졌다.** 창이 확장되지 않으므로
중재할 대상이 없다.

## 3. 새 모델을 고르는 근거

### 3.1 이 모델이 지우는 문제들

7-26 판이 풀려던 문제와, 그동안 별건으로 쌓여 있던 항목들이 함께 사라진다.

| 사라지는 문제 | 출처 | 왜 사라지나 |
|---|---|---|
| 작은 뷰포트에 UI 패널을 띄울 자리가 없다 | 이 문서의 원래 문제 | 창이 항상 작업 영역이라 패널이 언제나 들어간다 |
| 세로로 줄이면 패널이 잘린다 | 7-26 판 §2 | 창 크기가 변하지 않으므로 배율이 상수다 |
| 상시 HUD가 작은 뷰포트에서 읽기 어렵다 | `ViewportStackMigration.md` §6.4-17 | 위와 같은 이유 |
| CanvasScaler 정책 미결 (Constant냐 ScaleWithScreenSize냐) | `UIMenuBarDesign.md` §7 | 창이 상수면 두 모드의 차이가 거의 없어진다. 넘침 위험이 사라져 **Constant Pixel Size가 다시 후보가 되고**, 그러면 기획 §2.1.1의 "UI 크기 0.5x~1.5x"를 `scaleFactor`에 그대로 걸 수 있다 |
| 확장 요청 중재(`_isEditing` 참조 카운트화) | `ViewportStackMigration.md` §8 후속 2 | 확장 자체가 없다 |
| 확장 중 창 드래그가 뷰포트 설정을 덮어쓴다 | 7-26 판 §5.2 | 창 드래그가 없다 |
| 패널 여닫을 때 창 확장·축소 깜빡임 | 7-26 판 §7 4단계의 위험 | 창이 크기를 바꾸지 않는다 |
| `_floorY = 11.4444` 하드코딩이 작업표시줄을 추적하지 않음 | `ViewportStackMigration.md` §3.1 | 베이스 공간이 작업 영역이면 지면이 자연히 작업표시줄 위에 서고 재조정 때 따라온다 |
| 평시 캡션 존(220×28)이 콜라이더·UGUI보다 우선 | 핸드오버 §6 보류 3 | 캡션 존이 없다 |
| `_maxSize` 1920×1080이 4K에서 리사이즈를 제한 | 핸드오버 §6 보류 5 | OS 리사이즈가 없다 |
| EnterEdit 직후 `Screen.width/height`가 1~2프레임 stale | 핸드오버 §6 보류 7 | 창 크기가 안 바뀌므로 stale해질 일이 없다 |

### 3.2 작업표시줄을 비우는 것이 안전장치가 된다

창이 작업표시줄을 덮지 않으면, 클릭 통과가 고장 나도 사용자는 작업표시줄에 닿을 수 있다 —
다른 앱으로 전환하거나 우클릭으로 이 앱을 닫을 수 있다. 강제 종료 말고 길이 하나 생긴다.

원시 함수는 이미 있다. `WindowManager.ApplyMaximizeToWorkArea()`가 `rcWork`를 쓴다
(`WindowManager.cs:279-282`). 반면 `ApplyMonitorFullscreen()`은 `rcMonitor`를 쓰고,
`TryGetMonitorRect()`도 `rcMonitor`를 돌려준다 — 이쪽이 작업 영역 기준으로 바뀌어야 한다.

> **기하학만으로는 부족하다.** 작업표시줄 자동 숨김을 켜면 `rcWork`가 모니터 전체가 되어 이 방어가
> 사라진다. 세 겹으로 둔다.
>
> 1. **작업표시줄 제외** (이 결정)
> 2. **전역 핫키 강제 해제** — `OutFocusKeyHook`/`GlobalKeyInput`이 이미 있고, 기획 §2.4의
>    Boss Key(F2)가 그 자리다. `UIMenuBarDesign.md` §6-A가 잠금 기능을 뺀 이유도 정확히
>    "풀어줄 전역 핫키가 없어서"였다 — 같은 선행 조건이다
> 3. **suspend 자가 복구** — `WindowGuideUGUIMigrationPlan.md` §4.2의 제안. 한쪽 방향으로만
>    세우는 플래그를 상태에서 파생되는 값으로 바꾼다

### 3.3 `camera.rect`가 필요 없는 이유

뷰포트 밖을 안 그리려고 렌더링을 자를 필요가 없다. **뷰포트 밖에는 원래 아무것도 없기 때문이다** —
빈 곳은 알파 0으로 남아 바탕화면이 비친다. 뷰포트는 "무엇을 그릴지"가 아니라 **"게임 오브젝트가
어디까지 갈 수 있는지"** 를 정하는 사각형이다.

이건 기획서 §2.1.1의 서술과도 맞는다. 뷰포트 밖으로 나간 시설물은 인벤토리로 회수되고 캐릭터는
뷰포트 안으로 재스폰된다 — 즉 **뷰포트 밖에 남는 것이 없는 것이 정상 상태**다. 잘라낼 것이 없다.

그래서 `Camera.ScreenToWorldPoint`가 `camera.rect` 설정 하에서 어떻게 동작하는지의 미검증 위험이
아예 생기지 않는다. `WindowManager.PollClickThrough`(`WindowManager.cs:378`)의 클릭 통과 판정 경로가
지금 그대로 유지된다.

> **다만 나중에 조건이 생긴다.** 뷰포트보다 큰 월드 배경 스프라이트가 들어오면 뷰포트 밖으로 삐져나가고,
> 그때는 잘라낼 것이 생긴다. 현재 배경 렌더러는 없다. 배경을 넣을 때 다시 판단할 항목으로 §7.4에 남긴다.

### 3.4 성능 — 무엇을 포기하는가 (정직하게)

**뷰포트를 줄여서 얻던 절감이 사라진다.** 이게 이 결정의 유일한 실질 비용이다.

핸드오버 §2는 `useFlipModelSwapchain: 0`(BitBlt) 때문에 합성 비용이 창 면적에 비례하고
"성능 병목은 폴링이 아니라 렌더링과 창 면적임 (검증됨)"이라고 적고 있다. 1920×1080 모니터에서
720×480 뷰포트는 면적이 16.7%다 — 약 6배 차이고, 4K에서는 4%까지 간다.

**완화 요소 두 가지.**

1. **지금 기본값은 이미 전체 면적을 낸다.** `ViewportScreenSettings._viewport`의 기본값이
   `RectInt(0,0,0,0)`이고, 크기가 0이면 베이스 공간 전체로 채워진다
   (`ViewportScreenSettings.cs:82-83`). 즉 새로 생기는 비용이 아니라, **줄이려는 사용자가
   얻을 수 있었던 절감을 못 주게 되는 것**이다. 작업 영역은 모니터 전체보다 오히려 조금 작다.
2. **창 rect는 계속 정책 레이어가 소유하는 값이다.** `ApplyRegion(x, y, w, h)`이 이미 임의 rect를
   받는다. 나중에 "컴팩트 모드"(창을 뷰포트에 맞추고 메뉴 바를 뷰포트 모서리로 옮김)를 열 여지가
   구조적으로 남아 있다. **지금 만들지는 않는다.**

**그래도 남는 우려**: 뷰포트를 줄이는 사용자는 자원 점유에 가장 민감한 사람일 가능성이 높다.
그 사람에게 절감을 못 주는 셈이다. 면적이 고정된 이상 남는 지렛대는 프레임 레이트뿐이고
(`PerformanceSettings`가 이미 foreground/background를 전환한다), 유휴 상태 fps 인하가 이 모델에서
더 가치 있어진다. 별건 후속으로 §7.5에 남긴다.

## 4. 좌표계 — 창 크기가 바뀌어도 화면이 움직이지 않는다

`BaseSpaceCameraFitter.Frame(rect, baseSpaceSize)`는 `orthographicSize`를 rect 높이에 맞추고
카메라를 rect 중심에 놓는다. 이때 **화면상 절대 좌표에서 rect가 약분되어 사라진다.**

기호: `M` = 창이 놓이는 스크린 좌표 원점, `B` = 베이스 공간 크기, `v` = 프레이밍 rect,
`L = BR.x − B.w/ppu`, `Bot = BR.y` (`BR` = `_masterCanvasBottomRight`), `P` = 월드 점.

카메라 중심 `C.x = L + (v.x + v.w/2)/ppu`, 가로 반폭 `= orthoSize · aspect = v.w/(2·ppu)`.
창 안 픽셀 x는 `(P.x − C.x)·ppu + v.w/2`이므로,

```
절대 화면 x = M.x + v.x + (P.x − C.x)·ppu + v.w/2
            = M.x + v.x + (P.x − L)·ppu − v.x − v.w/2 + v.w/2
            = M.x + (P.x − L)·ppu          ← v가 사라진다
```

세로도 대칭이다 (`절대 화면 y(위 기준) = M.y + B.h − (P.y − Bot)·ppu`).

### 4.1 이 보증의 정확한 범위 (2026-07-27 정정)

**처음에 이 절은 "창 크기가 어떻게 바뀌어도 화면상 위치가 불변"이라고 적었는데, 그건 틀렸다.**
검수에서 잡혔다. 위 식을 끝까지 풀면 약분된 것이 무엇인지 분명해진다.

```
L = BR.x − B.w/ppu 를 대입하면
절대 화면 x = M.x + B.w + (P.x − BR.x)·ppu = (작업 영역 오른쪽 변) + (P.x − BR.x)·ppu
절대 화면 y = M.y + B.h − (P.y − BR.y)·ppu = (작업 영역 아래 변) − (P.y − BR.y)·ppu
```

**약분된 것은 프레이밍 rect `v`이지 베이스 공간 `B`가 아니다.** 정확한 보증은 이것이다.

> 화면상 위치·크기는 **작업 영역의 우하단 모서리에 고정**된다.

옛 모델에서는 "창 크기 변경"이 곧 `v` 변경이고 `B`(모니터 해상도)는 상수였으므로 위 식이 그대로
"창이 바뀌어도 불변"을 뜻했다. **그런데 새 모델은 창 = 베이스 공간이라, "창 크기 변경"이 곧
`B` 변경이다.** 그래서 §4의 유도는 재조정 버튼에 대해 아무것도 보증하지 않는다.

반례: 작업표시줄을 아래에서 위로 옮기고 재조정을 누르면 `B`는 1920×1032로 그대로지만
`M.y`가 0 → 48로 바뀐다. 작업 영역 아래 변이 1032 → 1080으로 내려가므로 **캐릭터도 48px 내려간다.**
이건 버그가 아니라 의도된 동작이다 — 지면이 작업 영역 바닥을 따라가는 것이 이 모델의 정의다.

### 4.2 그래서 실제로 보증되는 것

| 상황 | 화면상 위치 |
|---|---|
| 뷰포트를 바꾼다 (창은 그대로) | **불변** — 뷰포트는 렌더링에 관여하지 않는다 |
| 재조정: 작업 영역 우하단 모서리가 그대로 (예: 왼쪽 작업표시줄 폭 변경) | **불변** |
| 재조정: 우하단 모서리가 움직임 (예: 작업표시줄이 아래↔위) | **모서리가 움직인 만큼 따라 움직인다** (의도된 동작) |

> **확실성**: `BaseSpaceCameraFitter.cs:66-74`의 식에서 유도했고, 검수에서 반례 검증까지 거쳤다.
> 빌드 검증은 §6의 verify로 한다.

## 5. 기존 코드를 어떻게 다룰까

### 5.1 창의 크기·위치를 정하는 경로

지금 `ViewportScreenSettings.ApplyNormal()`이 뷰포트를 스크린 좌표로 바꿔 `ApplyRegion`을 부른다
(`ViewportScreenSettings.cs:211-220`). 새 모델에서 이 함수는 **창을 건드리지 않는다** — 창은
작업 영역에 고정이고, 뷰포트가 바뀌어도 창은 그대로다. `ApplyNormal`이 하던 일 중 남는 것은
`ViewportApplied` 이벤트 발행뿐이고, 카메라 프레이밍은 재조정 때만 일어난다.

필요한 것:

- `WindowManager`에 **작업 영역 rect를 돌려주는 API**. `TryGetMonitorRect`가 `rcMonitor`를 쓰므로
  `rcWork` 버전이 필요하다. `MONITORINFO.rcWork`는 이미 읽고 있어서(`TryGetMonitorInfo`) 추가는 작다.
- 창 rect를 **영속화**하고, 부팅 시 현재 작업 영역과 비교한다.

> **부팅 시 불일치 처리는 이 문서의 판단이다.** 국기님 요구는 "재조정 버튼을 누를 때만 바뀐다"였지만,
> 모니터를 더 작은 것으로 바꾸면 저장된 창이 화면 밖으로 나가 조작 불가가 된다. → **줄이는 방향만
> 자동 보정**하고(현재 작업 영역 안으로 클램프), 키우는 방향은 버튼을 누를 때만 한다. 자동으로
> 커지지 않으므로 "평상시 창은 변하지 않는다"는 요구는 지켜진다.

### 5.2 창 조작 기계장치 — deprecated로 살린다 (국기님 결정)

창이 정적이면 `WndProc` 서브클래싱·NCHITTEST·8방향 핫존·`WM_EXITSIZEMOVE` 역동기화가 전부
쓰이지 않는다. **다만 지우지 않는다.** 국기님 판단대로 상당 부분이 뷰포트 리사이즈에 재사용된다.

| 요소 | 재사용 가능성 |
|---|---|
| `HitTestCalculator` / `ResizeHitZone` | **높다.** `Calculate(mouseX, mouseY, left, top, right, bottom, …)`으로 rect를 인자로 받는다(`WindowManager.cs:390-393` 호출부). 창 rect 대신 **뷰포트 rect**를 넘기면 그대로 8방향 판정기가 된다. `UnityEngine` 의존이 없어 EditMode 테스트도 그대로 산다 |
| `WndProc` / NCHITTEST 응답 | **없다.** 뷰포트는 OS 창이 아니므로 OS가 히트테스트해 줄 수 없다. 이 부분이 진짜로 죽는다 |
| `WM_EXITSIZEMOVE` 역동기화 | **없다.** 창을 사용자가 끌지 않는다 |

> **여기서 잃는 것을 정확히 적어둔다.** OS에 위임했기 때문에 공짜로 얻던 것들 — 리사이즈 커서 모양,
> 드래그 추적, ESC 취소 — 을 뷰포트 조작에서는 직접 만들어야 한다. `ViewportEditHandles`가 이미
> 인앱 드래그를 하고 있으므로 패턴은 있지만, 공짜였던 것이 일이 된다.

**deprecated 표시 방법**: 코드를 남기되 `GameScene`에서 `_resizable`을 꺼서 `InstallWndProc`이
실행되지 않게 한다(`WindowManager.cs:185`). 삭제 판단은 새 모델이 빌드에서 검증된 뒤 별건으로 한다.

### 5.3 `WindowGuideUGUIMigrationPlan.md` — 예정대로 진행 (국기님 결정)

창이 정적이면 "창 이동·리사이즈 안내"는 안내할 대상이 없다. 하지만 §5.2와 합치면 **그 컴포넌트는
없어지는 게 아니라 대상이 바뀐다** — 창 rect를 그리던 것이 **뷰포트 rect**를 그리게 된다.

그러면 평시에 뷰포트 경계와 이동 그립이 보이고, 그걸 끌어서 뷰포트를 옮길 수 있다.
7-26 판에서 "창 드래그로 펫 위치를 직접 옮기던 감각을 잃는다"고 적었던 손실이 이것으로 메워진다.

그리고 UGUI로 옮기면 부수 이득이 하나 더 생긴다. 그립이 UGUI가 되면
`WindowManager.PollClickThrough`의 UGUI 레이캐스트 분기(`WindowManager.cs:383`)에 자연히 편입되어,
`overResizeZone` 특수 처리와 그에 딸린 suspend 경로가 필요 없어진다 — 핸드오버 §6 보류 1번이
원래 노리던 "suspend 단일 실패점 해소"가 여기서 달성된다.

> **그 문서를 진행하는 사람이 알아야 할 것**: 산출물의 수요처가 "창 안내"에서 "뷰포트 안내"로
> 옮겨간다. 알파 기록 셰이더·전용 캔버스·hover 폴링 설계는 그대로 쓰이지만, **좌표의 출처가
> `Screen.width/height`(창)에서 뷰포트 rect로 바뀐다.** 그 문서 §3.2의 "stretch 앵커가 레이아웃을
> 대신한다"는 전제는 창 전체를 채울 때의 이야기라 다시 봐야 한다.

## 6. 이행 계획

**전제**: `feature/viewport-stack`이 마무리 중이다. 그 브랜치가 만지는 파일
(`GameScene.unity`, `Scripts/CLAUDE.md`, `PerformanceSetting/CLAUDE.md`, `ViewportStackMigration.md`)은
건드리지 않는다. 구현은 그 브랜치가 `develop`에 합쳐진 뒤 시작한다.

창 관련 동작은 전부 `#if !UNITY_EDITOR` 안이라 **빌드에서만 검증된다**(핸드오버 §7).

### 0단계 — 안전장치 먼저

새 모델에서는 창이 작업 영역 전체를 덮으므로 클릭 통과 고장의 파급이 커진다. **모델 전환보다
안전장치를 먼저 넣는다.** §3.2의 2·3번(전역 핫키 해제, suspend 자가 복구).

- **verify**: 편집 모드 진입 후 컴포넌트를 강제로 파괴해도 클릭 통과가 스스로 복구되는가.
  핫키로 강제 해제가 되는가.

### 1단계 — 작업 영역 API와 베이스 공간 재정의

`WindowManager`에 작업 영역 rect API 추가. `ViewportScreenSettings.RefreshBaseSpace`가
그것을 쓰도록 변경. 창은 아직 뷰포트를 따라간다(동작 변화 최소).

- **verify**: 베이스 공간 크기가 작업표시줄을 뺀 값으로 나오는가. 캐릭터 지면이 작업표시줄 바로 위인가.
  이때 `ViewportStackMigration.md` §3.1의 `_floorY` 보정값이 이중 보정이 되므로 **함께 되돌려야 한다** —
  §7.2 참조.

### 2단계 — 창을 정적으로 (핵심)

`ApplyNormal`에서 창 배치를 떼어낸다. 창은 부팅 시 작업 영역으로 한 번 잡고, 카메라는
베이스 공간 전체를 프레이밍한다. 뷰포트는 이벤트만 발행한다. `_resizable`을 끈다.

- **verify (핵심)**:
  1. 뷰포트를 작게(720×480) 저장해도 **창 크기가 변하지 않는다**
  2. 그 상태에서 메뉴 바가 **화면 우하단**에 있다 (§2.1의 원래 문제)
  3. 상점·도감 패널이 잘리지 않고 온전히 보인다
  4. 작업표시줄이 **가려지지 않고 클릭된다** (§3.2)
  5. 뷰포트 밖 빈 곳 클릭이 뒤 앱으로 통과한다
  6. 캐릭터 크기·위치가 이전 빌드와 같다 (§4의 유도 확인)

### 3단계 — 재조정 버튼

설정 패널에 "윈도우 크기 재조정"을 추가. 창 rect 영속화 + 부팅 시 축소 방향 자동 보정(§5.1).

- **verify**: 작업표시줄 위치를 옮긴 뒤 버튼을 누르면 창이 새 작업 영역에 맞는가.
  버튼을 안 누르면 그대로인가. 해상도를 낮췄을 때 조작 불가 상태가 되지 않는가.

### 4단계 — 뷰포트 조작 UI

`WindowGuideUGUIMigrationPlan.md`의 이관을 뷰포트 rect 기준으로 진행(§5.3).
`HitTestCalculator`를 뷰포트 rect로 재사용.

- **verify**: 평시에 뷰포트 경계가 보이고 그립으로 옮길 수 있는가. "보이는 곳 = 잡히는 곳"이 유지되는가.

### 5단계 — 문서 반영

두 `CLAUDE.md`, 핸드오버 §2의 결정표(평시 창=뷰포트 항목이 낡는다), 이 문서 §8에 실측 기록.

## 7. 남는 결정과 후속

### 7.1 기획 원본 반영이 필요하다

기획서 §2.1.1의 용어표에서 **두 줄**이 낡는다. **저장소의 `Docs/Planning/UserSettings.md`는
사본이므로 여기서 고치지 않는다** — Figma·Notion의 원본을 고쳐야 하고, 그 전까지 두 줄은
낡은 상태로 남는다.

| 용어 | 기획서의 현재 정의 | 새 모델에서 |
|---|---|---|
| 베이스 공간 | "항상 모니터 해상도와 같은 크기" | **작업 영역**과 같은 크기 |
| 뷰포트 | "베이스 공간 중 **실제로 화면에 보이는 영역**" | 보이는 영역이 아니다. 캐릭터가 살 수 있는 영역이고, 뷰포트 밖도 화면에는 보인다 |

두 번째가 더 큰 변경이다. 뷰포트가 "보이는 영역"이 아니게 되므로, 기획서가 뷰포트로 설명하던
사용자 경험("보이는 영역을 조절한다")을 "펫이 사는 영역을 조절한다"로 다시 쓸지 판단이 필요하다.

취지 자체는 어긋나지 않는다. §2.1.1이 베이스 공간을 "시설물·캐릭터를 배치할 수 있는 전체 바탕 공간"으로
설명하는데, 작업표시줄 밑은 애초에 배치할 수 없는 자리다.

### 7.2 `_floorY` 보정을 되돌려야 한다

`ViewportStackMigration.md` §3.1이 `_floorY`를 `7 → 11.4444`로 올려 작업표시줄 높이(48px)를 보정했고,
2026-07-25 빌드로 확인했다. **베이스 공간이 작업 영역이 되면 이 보정은 이중 보정이 되어
캐릭터가 작업표시줄 높이만큼 떠 보인다.** 1단계에서 함께 되돌린다.

되돌린 뒤에는 그 문서가 경고한 "이 값은 작업표시줄을 추적하지 않는다"는 문제도 함께 사라진다.
그 브랜치가 머지된 뒤에 손대는 것이라 지금은 기록만 한다.

### 7.3 "공간 크기(줌) 0.5x~1.5x"와의 상호작용 (미해결)

기획 §2.1.1에는 인게임 전체 표시 배율 항목이 있다. 이걸 넣으면 `orthographicSize`가 바뀌어
**1 베이스 픽셀 = 1 화면 픽셀이 깨진다.** 그러면 "뷰포트 = 베이스 공간 px 사각형"이 화면 위에서
차지하는 크기가 배율에 따라 달라진다. 뷰포트를 베이스 공간 px로 정의할지 화면 px로 정의할지가
그때 갈린다. **지금 결정하지 않는다** — 줌은 미구현이고, 근거 없이 미리 정하면 틀린 쪽으로 굳는다.

### 7.4 월드 배경이 들어올 때의 클리핑 (미해결)

§3.3 — 뷰포트보다 큰 배경 스프라이트가 들어오면 잘라낼 것이 생긴다. 그때 `camera.rect`나
스텐실·마스크를 다시 검토한다. 현재 배경 렌더러는 없다.

### 7.5 프레임 레이트가 남은 지렛대 (후속)

§3.4 — 창 면적이 고정되면 비용을 줄일 수 있는 축은 fps뿐이다. `PerformanceSettings`가 이미
foreground/background를 전환하므로, 캐릭터가 유휴 상태일 때 더 낮추는 것을 검토할 여지가 있다.
**측정 없이 손대지 않는다.**

### 7.6 메뉴 바가 상시 노출된다 (확인 필요)

창이 작업 영역이면 메뉴 바가 항상 화면 우하단에 떠 있다. 뷰포트를 아무리 줄여도 메뉴 바는 그대로다.
자동 숨김이 필요한지는 기획 판단이라 여기서 정하지 않는다. 기획 §2.2의 "카운트 자동 숨기기"는
카운트 전용이라 이 항목을 다루지 않는다.

# WS_EX_TRANSPARENT ON 시 Unity의 마우스 입력 감지

2026-05-23

Project Cozy는 바탕화면 전체를 게임 화면으로 점유하면서 사용자의 평소 업무를 방해하지 않아야 한다. 게임 화면이 모니터 전체를 덮지만 캐릭터나 별 같은 게임 오브젝트(콜라이더) 위가 아닐 때는 마우스 클릭이 뒤의 프로그램으로 통과되어야 한다는 뜻이다.

Windows에는 윈도우의 클릭 투과를 제어하는 `WS_EX_TRANSPARENT` 확장 스타일 비트가 있다. 평소엔 ON으로 켜두어 모든 클릭이 통과되게 하고, 마우스가 게임 오브젝트 위로 들어왔을 때만 OFF로 바꾸는 동적 토글 방식이 자연스럽게 떠오른다.

그런데 이 접근은 한 가지 가정에 의존한다. 클릭 투과가 ON인 상태에서도 Unity가 마우스 위치를 계속 알 수 있어야 한다는 것이다. 만약 ON일 때 Unity가 마우스 위치를 받지 못한다면 "마우스가 게임 오브젝트 위로 들어왔다"는 트리거 자체가 발생하지 않으니, 한 번 ON이 된 후엔 영원히 OFF로 돌아오지 못하는 치명적인 데드락이 생긴다.

이런 가능성이 실제로 있는 이유는, `WS_EX_TRANSPARENT`가 활성화되면 OS가 마우스 메시지를 우리 윈도우로 보내지 않고 아래 윈도우(메모장 같은)로 직접 라우팅해 버리기 때문이다. Unity가 마우스 위치를 어떻게 읽느냐에 따라 — OS 메시지 기반이면 freeze, 별도 폴링이면 계속 갱신 — 결과가 갈린다.

이 동작을 추측이 아니라 직접 확인하기 위해 작은 테스트 컴포넌트와 씬을 만들었다. `WS_EX_TRANSPARENT`를 강제로 ON 시킨 상태에서 매 프레임 `Mouse.current.position` (Unity New Input System)과 `GetCursorPos` (Win32 OS-wide)를 둘 다 화면에 표시하고, 비상 탈출용으로 F12 키 토글을 달았다.

빌드해서 마우스를 움직여 본 결과, `WS_EX_TRANSPARENT`가 ON인 동안에는 `Mouse.current.position` 값이 그대로 멈춰 있었다. 같은 시점에 `GetCursorPos` 값은 정상적으로 갱신되었으므로, freeze는 Win32 쪽이 아니라 Unity Input System 쪽에서 일어나고 있는 것이 확실하다. F12로 OFF로 토글하고 마우스를 게임 윈도우 위에 올리면 그때부터 다시 갱신이 된다.

결론적으로 `WS_EX_TRANSPARENT`가 ON인 동안 Unity는 마우스 위치를 알 수 없다. 클릭 투과 토글 컨트롤러를 만들 때는 Unity의 Input API에 의존하면 안 되고, 별도로 `GetCursorPos` 또는 동급의 OS-wide API로 마우스 위치를 폴링해서 그 좌표를 기준으로 콜라이더 hit-test를 수행해야 한다.
